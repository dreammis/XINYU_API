# XY API 文档改版方案：参考 APIMart

日期：2026-10-09；实施更新：2026-10-10。导航、首页、系列选型页、模型中心与接口模板已实现，发布与验收记录见 cloudflare-setup.md。TTS、音乐等新能力仍按接入验收顺序交付，本次改版不代表新增能力上线。

## 结论

APIMart 使用 Mintlify 构建和托管。值得借鉴的是以客户任务和模型系列为中心的导航，以及说明、参数、示例、调试一致的接口页面。本站目前先完成了多工程契约汇总与托管，客户使用路径和页面层次仍不完整。

推荐保留已部署的 Cloudflare Pages、VitePress/Vue、公开契约汇总及本站调试代理，重做导航、模型目录和页面模板。导航变化与框架迁移是两件事；现有问题可以在当前框架中解决，不需要为分类改版重写托管链路。

## 参考站的事实与技术栈边界

已读取 [APIMart 中文首页](https://docs.apimart.ai/cn)、[模型元数据页](https://docs.apimart.ai/cn/api-reference/texts/models/list)、[TTS 页面](https://docs.apimart.ai/cn/api-reference/audios/tts) 与 [llms.txt](https://docs.apimart.ai/llms.txt)，并实际查看首页浏览器截图和导航 DOM。

- 首页和 llms.txt 的页脚明确声明由 Mintlify 构建和托管，因此文档平台有直接证据。
- 顶部四个栏目是 API 手册、集成指南、用户指南、常见问题；左侧按文字、图像、视频、音频等系列组织。
- 图像和视频系列中有可展开的模型分组，接口条目带 GET/POST 标签。普通说明页右侧有本页目录。
- 当前参考站把 TTS、音频转录与音乐放在音频系列中；本站可以根据产品规模把 TTS、音乐、转写分别列为系列。
- 它公开了 OpenAPI 下载入口与机器可读的文档索引。模型页说明支持分类、能力标签和参数契约，但这些是它的客户接口功能，不能直接作为本站功能承诺。

Mintlify 官方说明其标准工作方式是 Markdown/MDX 内容、docs.json 导航、OpenAPI 接口定义和 Git 同步部署；这些是平台能力，不能凭公开页面断言 APIMart 每页都采用完全相同的维护方式。公开页面也不能判断 APIMart 业务网关的后端语言、数据库、渠道路由实现或实际套餐。

官方依据：[导航配置](https://www.mintlify.com/docs/organize/navigation)、[接口页与调试](https://www.mintlify.com/docs/api-playground/overview)、[Git/MDX 工作方式](https://www.mintlify.com/docs/quickstart)。

## 当前问题与原因

| 问题 | 本地证据 | 客户受到的影响 | 改版动作 |
| --- | --- | --- | --- |
| 同一能力分散在两个目录 | 生成的 SUMMARY 有“能力指南”与“API Reference”，两边都有图片和视频 | 不知道先读哪一份，参数与限制需要往返找 | 在同一系列下放总览、选型和接口 |
| 顶部 API Reference 直接进入图片生成 | site/.vitepress/config.mjs 固定指向 generate-image | 无法把它当作全站接口手册入口 | 顶部指向接口概览 |
| 模型目录只是名称列表 | build-docs.mjs 从 manifest.models 生成表格 | 能看到名字，但不知道能力差异、选哪个、如何调用 | 模型中心加入筛选、能力标签和系列详情 |
| 接口内容重复 | get-video.md 包含 ApiPlayground，后面又有 Markdown 参数表与响应示例；Scalar 同时渲染这些信息 | 页面长、双标题、重复字段，阅读和调试割裂 | OpenAPI 参数/响应只渲染一次 |
| 中文页面混入英文接口说明 | 参数表是 Name/In/Required，响应描述取英文 description | 中文阅读不连贯 | 全页面使用同一语言；需要的翻译来自公开契约 |
| TTS 放在开始使用 | content/navigation.json 把旧 TTS 指南列为入门条目 | 入门知识与产品接口混在一起 | 移入 TTS 系列；未验收内容不作可调用入口 |
| 快速开始首先介绍扩展 SSE 事件 | content/zh/quickstart.md 第一例含 stream:true、delivery:url | 第一次调用就要理解事件、心跳和兼容差异 | 最小成功请求优先；扩展协议独立讲解 |
| 数据不足以自动生成模型选型 | 当前清单只有能力名称、版本和 models 字符串数组 | 文档 AI 容易凭模型名猜能力，或手工维护第二份目录 | 接入层交付分类、分组和经过确认的模型差异 |

当前导入的图片契约有 10 个公开调用名称，视频契约有 4 个。名称属于本站公开路由，不能自动推断为原厂模型身份。TTS 原有指南明确记录客户响应尚待核对；其他源工程即使已经有功能，也不能据此进入可用模型目录。

## 内容组织规则

客户需要解决三类问题：平台提供什么、选哪种能力或模型、怎么调用并拿到结果。目录按这个顺序组织。

| 信息 | 内容是什么 | 在哪里维护 |
| --- | --- | --- |
| 系列分类 | 文字、图像、视频、语音 TTS、音乐、转写、工具服务 | 文档工程定义稳定分类；源清单声明所属分类 |
| 模型或产品系列 | 经过确认的公开模型分组及各模型差异 | 客户接入代码旁的公开清单与指南 |
| HTTP 接口 | 路径、方法、鉴权、参数、schema、响应 | public-openapi.json |
| 使用流程 | 如何选参数，创建/查询/下载，计费、错误和恢复 | 中英文公开指南 |
| 渠道/源工程 | 内部供应商、部署、映射和来源 SHA | 内部配置与 provenance；不作为客户主目录 |

同一协议下的多个模型共用接口定义，模型页补充选择、限制和调用示例。只有路径、schema 或流程存在真实差异时，才拆出独立接口说明。分类按经过确认的数据生成，不从模型名、工程名或渠道名推断。

## 推荐顶层结构

顶部主导航：**API 手册 / 模型中心 / 接入指南 / 常见问题**。

搜索、语言、主题、控制台属于全站功能，放在同一条全局栏。变更记录可放在常见问题或页脚，资料达到规模后再提升为主导航。

API 手册侧栏目标如下。带“验收后”的部分描述未来结构，正式导航只显示已交付和验收的内容。

```text
API 手册
  概览
    平台介绍与第一次调用
    服务地址与客户 Key
  模型与能力
    模型中心（链接到同一目录）
    模型列表 API（客户接口验收后）
  图像系列
    图像总览与模型选择
    模型系列与差异（源工程确认分组后生成）
    POST 生成图片
    POST 编辑图片
    图片流式与进度
  视频系列
    视频总览与模型选择
    文生 / 单图生 / 多参考图生的参数示例
    POST 创建视频任务
    GET 查询视频状态
    GET 下载视频
    Responses 流式与后台调用
    HEAD 检查文件（归入高级使用）
  语音 TTS 系列（验收后）
    语音总览 / 音色 / 合成 / 下载
  音乐系列（验收后）
    音乐总览 / 生成 / 查询 / 结果获取
  文字系列（验收后）
    模型选择 / 对话 / 多模态 / 流式
  转写系列（验收后）
    音频输入 / 转写 / 字幕与结果
  工具服务（验收后）
    搜索 / 文件处理 / 其他计费功能
```

普通能力中“系列 → 总览/模型选择/操作”保持主要导航层级，模型多时分组折叠。选中页面自动展开所属组，不默认展开全部模型。请求方法采用小标签，标题使用“生成图片”等客户能理解的动作。

接入指南侧栏只放获取 Key、第一次调用、SDK/客户端接入、文件输入、长任务处理和计费规则；这些文档由接口页交叉链接，不复制正文。常见问题按鉴权、额度与计费、输入参数、长任务与结果获取组织。

## 首页：让客户知道下一步去哪里

首页首屏需要同时回答“能用什么”和“怎样开始”：

1. 简短的平台描述，明确统一客户入口；服务地址可复制。
2. 两个主动作：获取 API Key、完成第一次调用。
3. 按系列排列的入口，已发布系列显示进入按钮，未形成公开契约的系列不提供调用链接。完整类别可以出现在带状态的产品目录中，但不能显示成全部可用。
4. 下方放模型选择与常用任务的入口，例如生成图片、参考图编辑、生成视频、查询任务。
5. 一个经过验证的最小请求示例，cURL / Python / Node.js 切换。

不在首页堆长参数表、协议分支和每个模型的限制。首屏也不采用未经验证的“全模型”“原厂直连”“统一 token 计费”“SLA”等营销承诺。

第一次图片示例优先演示实际支持的普通 JSON 调用，stream、progress、delivery 等扩展参数另有指南。视频第一次调用按创建 → 查询 → 下载完整展示，不把创建任务成功当成得到成品。

## 模型中心：解决选型，而不只是罗列名称

目录默认按已发布的公开调用名称展示，支持按系列、输入输出类型、调用模式筛选。搜索既支持名称，也支持“图生视频”“文字转语音”等任务词。

每个条目展示：公开调用名称、所属系列、已确认的用途、输入输出、关键限制、计费单位、调用入口。公开产品别名与原厂模型名称不混为同一个字段；不能凭名称补写厂商或性能排名。

模型详情页应包含：

- 适用任务及经过确认的能力差异。
- 参考图、尺寸、时长、输出格式等适用限制。
- 最小完整调用示例，以及适用接口链接。
- 计费单位与价格查询入口；固定价格需要注明适用分组和版本来源。
- 异步/流式流程与结果获取方式。
- 未支持参数和常见错误。

模型页与接口页引用同一份 OpenAPI，不维护第二份完整参数 schema。差异数据由接入任务交付。例如快照中已记载：图片 Lite 限于 1K，某些 GPT 路由的正方形 4K 档实际像素不等于 4096；视频 short 固定时长、且不接受图生输入。这类差异应直接出现在选择页，不能藏在长指南中。

当前仅有名称数据，因此第一阶段可以先建立系列总览和已有指南中的对照表。未经接入任务确认的模型分组、结构化差异与“推荐”不得自动生成。

## 接口页：导航、说明、代码各占一处

桌面版目标：

```text
┌─────────────────────────────────────────────────────────────┐
│ XY API    搜索                         中文 / 主题 / 控制台   │
│ API 手册        模型中心        接入指南        常见问题       │
├──────────────┬───────────────────────────┬──────────────────┤
│ 系列目录     │ 图像 / 生成图片            │ cURL / Python    │
│ 当前组展开   │ 标题与一句用途             │ 请求示例         │
│              │ POST /v1/images/generations│                  │
│ 图像系列     │ 支持模型 / 输入 / 输出     │ 响应示例         │
│   模型选择   │ 鉴权与最小调用             │                  │
│   生成图片 ● │ 参数（只出现一次）         │ 试一试           │
│   编辑图片   │ 成功响应、错误、计费       │                  │
│ 视频系列     │ 下一步：编辑/查询/下载     │                  │
└──────────────┴───────────────────────────┴──────────────────┘
```

普通指南使用左目录、正文、右本页目录。接口页的右栏用于代码和响应，不同时塞入第二个目录或完整文档组件。移动端使用单列，代码与调试收进可展开区域，目录通过抽屉打开。

统一一个页面标题、一个鉴权入口、一套参数说明。当前完整 Scalar 文档内嵌再追加 Markdown 表格的方式要替换：可先让 Scalar 成为接口信息的唯一渲染者、去掉外围重复表格；随后再按选定的三栏模板整合独立 API 客户端。独立客户端与代码组件先验证官方 API、版本、流式和文件行为，不能靠全局 CSS 隐藏 Scalar 内部结构来假装完成整合。

调试继续使用本站 `/api-proxy` 与客户自己的 Key。示例代码始终使用占位 Key，浏览器不持久化真实 Key；正常请求仍按服务规则计费。文字、JSON、SSE 与二进制媒体的响应展示按真实协议实现，不能把任意 JSON 内的 URL 都当作成功媒体产物。

中文页面的参数名保持协议原名，标题、必填标签、错误和解释使用中文；英文站使用同版本英文内容。参数说明缺翻译时由公开契约维护任务补全，不在前端推测翻译和限制。

## 视觉方向

采用简洁的开发者文档设计：浅色默认、白底、细分隔线、少量品牌色。分类图标、方法标签和选中状态帮助定位，内容优先于装饰。

- 导航宽度约 256–280px；接口正文与代码栏按屏幕宽度分配。
- 主标题清楚，正文约 15–16px；长表格转为字段列表，嵌套字段可展开。
- 通用栏目与当前系列有明确边界，滚动时全局导航稳定。
- 避免大块渐变、无用仪表盘、重复标题和首页过度营销。
- 复制服务地址、请求示例与响应示例有直接反馈。

这些是设计起点，落实时以 1440px、1024px 和 390px 等典型宽度验证，不把固定尺寸强塞到移动端。

## 技术选择

| 方案 | 能解决什么 | 本次判断 |
| --- | --- | --- |
| Mintlify 托管 | 已有完整导航、内容组件与接口页体验 | 参考它的设计。若决定购买或接入，需另核对套餐与功能；本次不要求迁移 |
| VitePress + Vue 定制 + Scalar + Cloudflare | 复用已经部署的内容、构建、搜索与调试代理，改导航与页面呈现 | 推荐。VitePress 支持自定义主题与 Vue 交互组件，并非只能使用默认文档布局 |
| Next.js + Fumadocs | 使用 React 文档组件和布局系统重新组织页面 | 可选，适合以后文档与 React 产品深度整合；当前会增加迁移、静态构建与托管验收工作 |

参考：[VitePress 自定义能力](https://vitepress.dev/guide/what-is-vitepress)、[Fumadocs UI](https://www.fumadocs.dev/docs/ui)、[Scalar API Client](https://scalar.com/products/api-client)。本站 package.json 中仍有历史 Next/Fumadocs 依赖，但当前生产脚本是 VitePress；不能据依赖存在就把旧站当成当前发布版本。

## 接口来源需要补充哪些数据

现有 OpenAPI、指南和 public-docs.json 保留职责。公开清单现已支持可选 `category` 与按已有公开模型名索引的 `modelDetails`。具体格式、校验和选型章节引用规则见 [模型目录交付约定](model-catalog-contract.md)：

```json
{
  "category": "image",
  "modelDetails": {
    "gpt-image-2": {
      "group": "gpt-image",
      "title": { "zh": "GPT Image 2", "en": "GPT Image 2" },
      "operations": ["generateImage", "editImage"]
    }
  }
}
```

具体实施时同时升级清单校验、模板、源工程交付说明和站点生成器。现有 `models` 仍是已公开模型名称的唯一列表，`modelDetails` 的键必须属于该列表；引用的操作 ID 必须存在。分组、能力差异和限制由维护客户协议的任务确认，来源不完整时明确失败或保持未发布状态，不让文档 AI按名字猜测。

非模型能力 `models: []` 仍然成立，它只需要分类、指南与真实操作。多渠道共用同一客户协议时不重复生成系列和规范。分类/展示元数据与公开行为版本一起更新，来源 SHA 和哈希仍记录在 catalog 中。

先补充少量直接用于页面的元数据，不新增全局模型数据库、运营后台或多层管理器。指南暂时保留人工确认的差异表；只有需要筛选或自动表单的具体信息才结构化。

## 实施顺序和验收

| 顺序 | 交付 | 验收 |
| --- | --- | --- |
| 1. 重排目录与首页 | API 概览入口、按系列组织导航、图像/视频总览、旧 TTS 调整归属、简单快速开始 | 新用户从首页两次导航内找到当前图片或视频的最小调用；没有未验收能力的可调用入口 |
| 2. 统一接口页 | 唯一 OpenAPI 参数渲染、统一标题和语言、说明/代码/调试布局 | 当前 8 个操作信息完整，GET/POST/HEAD 明确，字段和响应不重复；移动端不横向挤压 |
| 3. 模型中心 | 已确认的模型分组、差异信息、筛选和模型详情 | 当前快照 14 个公开调用名可定位，各页引用同一规范；不同模型的实际限制可直接找到 |
| 4. 按 SOP 补齐系列 | TTS、音乐、文字、转写、工具按验收顺序导入 | 每项都有客户入口验收、计费语义、公开契约与来源记录 |
| 5. 发布与迁移核验 | 旧 URL 跳转、搜索、语言切换、代理与新页面校验 | 原链接不失效，新分类可搜到；构建、docs:check、测试和 Function 编译通过，Cloudflare 实际部署成功 |

改版要从目录数据和生成模板修改，不能手改生成页面。旧链接映射显式维护；不能删除全部旧页再声称迁移完成。现有来源同步与部署接线状态分别核验，不因 UI 改好就宣称上游全部接线完成。

主要改动位置：`content/navigation.json`、共用中英文页面、`scripts/build-docs.mjs`、`scripts/build-site.mjs`、`site/.vitepress/config.mjs` 与 theme。公开清单结构升级会涉及 `scripts/docs-contract.mjs`、清单模板、接入任务说明以及对应源工程的正式交付。

本文件保留原设计目标；实际部署、检查结论及尚未交付的数据，以维护验收记录为准。原始下载规范未因页面模板改造而改变。
