# 从工程 API 到客户文档：执行 SOP

这套流程适用于图片、视频、语音、搜索、转写、文件转换等能力，也适用于 New API 插件、内置渠道和独立适配服务。你负责决定要接入什么，各个工程的 AI 负责实现、验收和交接，文档工程的 AI 负责汇总发布。

你不需要手写 JSON，也不需要把接口文档抄两遍。每次只需把对应任务说明发给正在负责那一步的 AI，把上一步交付的文件路径或 Git 提交交给下一步。

## 先分清三个角色

| 角色 | 负责回答的问题 | 交付给下一步 |
| --- | --- | --- |
| 上游工程 AI | 功能如何调用，实际有什么限制？ | 已实现的接口、调用示例、测试结果、交接记录 |
| New API 接入 AI | 客户用自己的 Key 怎么调用，参数如何转换，怎么计费？ | 已启用的客户入口、验收记录、公开接口文件 |
| 文档工程 AI | 已验收的客户接口如何展示和更新？ | 来源登记、导入快照、文档页、调试页、发布结果 |

一个 AI 可以兼任上游和接入两个角色；职责仍需分别完成。不同任务不会自动共享聊天记忆，协作依据是可读的交接文件、代码提交和测试证据。交接时传路径与版本，不能只说“看我另一个任务”。

## 第一步：上游 API 调通后，先交付给接入任务

把 [上游工程任务说明](../../templates/ai-upstream-task.md) 的正文复制到对应工程的任务，补上功能名称；当前工程路径和仓库信息可以让该 AI 自己读取。

该 AI 核对实现，并输出：

1. 接口路径和方法，输入字段、默认值、限制、实际响应与错误。
2. 能复现的请求示例；异步任务包括创建、查询、下载，流式接口包括事件格式。
3. 验证命令与实际结果，部署版本和环境；本机测试不能写成已上线。
4. 用 [交接记录模板](../../templates/api-release-handoff.md) 建立一份文件，填写“上游交付”，给出绝对路径和 Git 提交。

这时的状态是“上游可用”，还不能对客户宣布“通过 New API 可用”。

## 第二步：交给 New API 接入任务，确定唯一的公开文档维护位置

把 [New API 接入任务说明](../../templates/ai-newapi-task.md) 和第一步的交接文件路径发给接入 AI。

公开文档放在**实现客户协议的代码旁边**，由接入 AI 维护：

- 插件就在源工程中：放在该工程的插件目录。例如 `vidu2api/integrations/newapi/media-image/`。
- 适配器实现在独立 New API 仓库：放在该仓库的对应适配目录，文档工程登记这个仓库。
- 两个工程由不同 AI 维护：上游 AI 维护内部调用说明，接入 AI 维护客户公开说明；二者通过交接记录说明映射关系。

目录名可以遵循原工程现有风格，汇总器不要求一定使用 `integrations/newapi/`。确定一个维护位置后不在另一个仓库复制第二份客户接口说明。

这里同时确定稳定的能力 ID，例如 `media-image`、`media-video`、`file-conversion`。ID 决定文档页面路径，不要随渠道名称改变。

## 第三步：验收客户入口和计费，再确认可发布

接入 AI 完成参数映射、客户 Key 鉴权、模型或功能路由、计费、结果转换，并在实际客户入口验收。是否使用插件由现有架构决定，不必为了文档额外做插件。

| 验收内容 | 需要的证据 |
| --- | --- |
| 正常调用 | 用客户 Key 发出的真实请求及脱敏结果；不能用管理员测试接口代替 |
| 参数转换 | 客户字段与上游字段的对应关系；不支持的参数明确报错 |
| 鉴权与输入错误 | 无效 Key、非法参数的实际状态码与响应 |
| 长任务 | 创建返回什么、如何查询或下载、连接中断后如何恢复 |
| 计费 | 一次成功调用的账单变化、计费单位、失败和取消的扣费或退款行为 |
| 部署版本 | 实际启用的插件或服务版本，时间和验收环境 |

使用现有授权的测试额度和凭证。没有真实业务验证条件的项目明确标记“待验证”，不把模拟成功、401、源码合并或插件上传当成完整上线验收。401 只证明鉴权链路可达，不能证明生成结果和计费正确。

价格可能随 New API 配置变化，指南写清计费单位、触发时机和查询价格的入口；固定数字只在有当前公开配置依据时写入，并说明需要同步维护。

接入 AI 在交接记录中填写“客户入口验收”。全部通过后状态才能改为“客户入口已验收”。上游响应和客户响应可能不同，例如上游返回音频 URL，客户收到的是音频二进制，公开文档必须写客户收到的结果。

## 第四步：接入 AI 交付四个公开文件

文件由接入 AI 根据真实实现和验收结果产生，你不用自己填写字段。

| 文件 | 用途 | 谁维护 |
| --- | --- | --- |
| `public-openapi.json` | 机器可读的接口定义：路径、鉴权、参数、响应和示例；用于生成参数页与在线调试 | 接入 AI |
| `public-guide.zh.md` | 中文调用指南：流程、限制、计费语义和完整示例 | 接入 AI |
| `public-guide.en.md` | 同一版本的英文指南 | 接入 AI |
| `public-docs.json` | 文件清单：能力 ID、名称、版本、公开模型名及上面三个文件的位置 | 接入 AI |

名称是 **OpenAPI**，不是 OpenAI。OpenAPI 是描述 HTTP 接口的格式，不局限于大模型，也不要求接口模仿 OpenAI。

已有中文指南可以直接复用，例如图片能力清单的中文入口是 `integrations/newapi/media-image/README.md`，视频能力是 `docs/video_studio_api.md`；不为统一文件名再抄一份。

清单格式以 [现有模板](../../templates/public-docs.json) 为准，下面是一个**格式示例，不代表已经上线了文件转换能力**：

```json
{
  "schemaVersion": 1,
  "id": "file-conversion",
  "title": { "zh": "文件转换", "en": "File conversion" },
  "version": "1.0.0",
  "models": [],
  "openapi": "integrations/newapi/file-conversion/public-openapi.json",
  "guides": {
    "zh": "integrations/newapi/file-conversion/public-guide.zh.md",
    "en": "integrations/newapi/file-conversion/public-guide.en.md"
  }
}
```

清单中的路径相对**存放清单的仓库根目录**，用 `/`，不能写磁盘绝对路径、`..` 或 `\\`。当前汇总器要求：

- OpenAPI 使用 3.1，`info.version` 与清单 `version` 相同。
- 规范有 HTTPS 客户服务器地址、鉴权定义、实际操作和响应。地址不能写上游内网或管理入口。
- 当前在线调试转发使用客户 Bearer Key，支持 GET、POST、PUT、PATCH、DELETE、HEAD。需要其他鉴权、额外请求头或方法时先由文档任务明确扩展实现，不能只在规范中增加便宣称调试已支持。
- 每个操作有唯一且稳定的 `operationId`；它影响接口页面地址。补充 `x-title-zh` 和 `x-description-zh` 可以让接口标题与说明显示中文。
- 两份指南以 `# ` 标题开头，内容与同一版本的实现一致。
- `$ref` 只能引用规范内部；外部 schema 先合并到该文件。
- 公开模型名与清单一致；非模型能力 `models: []`。当前校验器要求组件中的 `model.enum` 与清单模型列表一致。
- 指南应当可以独立阅读；当前只导入两份 Markdown，不会搬运源工程的图片或其他 Markdown 附件。确实需要扩展公开附件时由文档任务先修改导入机制。

语法校验通过只证明格式成立，源工程还要验证示例被真实适配器接受、实际响应与规范一致。`vidu2api` 已有示例校验命令 `node --test integrations/newapi/public-contract.test.mjs`；其他工程使用自己的实际适配器测试，不机械复制这个命令。

公开包不能包含客户 Key、管理员令牌、渠道密钥、内部运维地址或成本数据。交接中的内部证据也不列入 `public-docs.json`。

## 第五步：把发布交接记录交给文档工程任务

把 [文档工程任务说明](../../templates/ai-docs-task.md) 发给 `G:/workspace/xyapi_doc` 的任务，并附上接入 AI 填好的交接文件路径或 Git 地址。

文档 AI 需要的输入只有：

| 输入 | 说明 |
| --- | --- |
| 能力 ID 和名称 | 例如 `media-image` / 图片 |
| 公开文件的维护仓库 | 例如 `dreammis/vidu2api`；不一定是原始上游仓库 |
| 本机目录与清单路径 | 例如 `G:/workspace/vidu2api` 和 `integrations/newapi/media-image/public-docs.json` |
| 发布 ref 与契约提交 SHA | 必须能在 GitHub 读取到已发布文件；SHA 用于追溯本次版本 |
| 客户入口验收记录 | 是否已启用、真实请求结果、计费语义、测试与部署版本 |
| 新增还是更新 | 已登记能力的更新无需重新建立一套页面 |

发布 ref 是汇总器读取的 Git 分支、tag 或 SHA，**不是** `public-docs.json` 中的版本号。当前汇总器按 `sources.json` 的 ref 读取，不会自动寻找最新 tag，也不会解析交接记录来改变 ref。

首次能力在 `sources.json` 中增加一项。继续以上面的格式示例：

```json
{
  "id": "file-conversion",
  "repository": "dreammis/your-source-repo",
  "ref": "public-docs-live",
  "localDirectory": "../your-source-repo",
  "manifest": "integrations/newapi/file-conversion/public-docs.json"
}
```

这是添加到现有 `sources` 数组的示例，不要替换原有登记。该分支名仅作示范，实际 ref 必须存在并由接入任务确认。

文档 AI 在文档工程执行：

```powershell
# 首次安装依赖；已有依赖时无需重复安装。
npm ci

# 正式发布读取远端已发布契约；私有仓库使用已配置的 DOCS_SOURCE_TOKEN。
npm run docs:sync:remote
npm run build
npm run docs:check
npm test
```

联调可以用 `npm run docs:sync` 读取本机文件，随后执行同样的构建和校验；本机未提交文件会记录在 provenance 中。正式来源同步完成后，快照对应的远端提交必须包含全部公开文件。

当前同步器每次读取**全部登记来源**，不是只读取发通知的工程。任何已登记来源缺文件或无读取权限会阻止本次导入，不会跳过它然后宣称发布成功。首次接线要检查整个登记列表。

文档任务负责：验证输入、登记来源、导入、构建、检查页面、提交本次文档变化、确认 Cloudflare 部署成功，并把站点 URL 与部署版本回填交接记录。不凭上游文档重新猜客户参数，不手改 `catalog`、`gitbook` 或 `site/zh`、`site/en`。

本机文档目录仍有之前的前端工作。发布时使用已有适用的隔离工作区或基于远端生产分支准备提交，只带本次文档文件，不能直接 `git add .` 把历史和其他工作一起推上去。

## 第六步：第一次接线完成后，减少手工交接

先完成一次“接入 AI 交付 → 文档 AI 正式导入 → 客户站核验”的完整发布，再配置通知。

| 配置位置 | 一次性设置 |
| --- | --- |
| 公开文件维护仓库 | 把 [通知模板](../../templates/source-docs-sync.yml) 放到 `.github/workflows/public-docs.yml`；配置 `DOCS_DISPATCH_TOKEN`，用于通知 `dreammis/XINYU_API` |
| 文档仓库 `dreammis/XINYU_API` | 私有来源配置 `DOCS_SOURCE_TOKEN`，可读取全部登记的私有来源仓库 |
| 文档仓库 | 登记 `sources.json`；确认导入 workflow 能写回生产分支，分支保护规则允许该发布方式 |
| Cloudflare | 读取文档仓库 `master` 自动部署；这段接线此前已实际验证 |

两种 Token 职责不同：`DOCS_SOURCE_TOKEN` 读源仓库，通常只需来源仓库 Contents: read；`DOCS_DISPATCH_TOKEN` 调用文档仓库 repository_dispatch，GitHub fine-grained token 需要目标仓库 Contents: write。存入 Actions Secrets，不发到聊天正文或公开文件。

通知模板默认只有 `workflow_dispatch`。客户入口上线并验收后，由接入 AI 在 GitHub Actions 的 **Notify public docs release → Run workflow** 执行；选包含已验收公开文件的分支。文档仓库实际仍按登记 ref 读取，选择不同通知分支不会改变来源。

目前通知只发送事件 `public-docs-updated`，不携带接口正文或发布 SHA，也不自动证明运行版本。因此所有登记 ref 都要只包含已经发布的契约。最简单的规则是：实现可以先提交，面向发布的公开契约在客户入口验收后才更新。若开发需要提前修改契约，使用单独的已发布契约分支或固定 SHA；固定 SHA/tag 每次升级都需更新文档登记。

如果将来要做到完全自动，把通知步骤接到该工程**真实部署并完成客户入口验收之后**。有上线 workflow 就接在其成功步骤后，不额外制造发布框架。只有在公开文件更新必然发生在验收之后的工程，才适合按这些文件的 push 自动通知；普通 main push 不能替代上线验收。

接通后链路为：已验收契约发布 → 接入任务触发通知 → 文档工程读取已登记 ref → 校验并提交快照 → Cloudflare 自动部署。你无需再去文档工程填写接口参数。

## 日常变更、多个渠道与退役

| 变化 | 怎么做 |
| --- | --- |
| 新渠道，客户协议和计费语义完全相同 | 接入 AI 验收内部路由，复用同一能力文档；无公开行为变化时无需发布新接口页 |
| 同一能力新增公开模型或参数 | 接入 AI 更新清单、规范、指南与版本，验收后发布并通知 |
| 一个工程有多个能力 | 每个能力一个清单，分别登记；不按工程数决定页面数 |
| 不同工程提供同一客户接口 | 选择一个负责该客户协议的维护仓库，其余工程提供内部实现交接；不以同一个 ID 重复登记 |
| 客户流程、输入输出或计费规则不同 | 先判断同一指南能否明确表达差异；不能时建立独立能力 ID |
| 上游内部变化，客户行为没变 | 上游与接入任务核对兼容性；无需让文档任务重新抄写 |
| 价格变化 | 计费维护任务更新公开价格来源；指南如有固定价格也同步修订 |
| 回退 | 接入 AI 确认实际运行版本，文档 AI 读取对应已发布契约版本后重新构建；只回退网站不能回退服务 |
| 下线能力 | 先明确客户入口下线安排，再移除登记及共用指南链接、构建发布；不要仅删除生成页 |

同一路径可以用于不同能力，例如多个能力使用 `/v1/responses`。本工程按能力保存独立规范，避免合并时覆盖。渠道 ID、密钥与内部路由不是能力 ID。
