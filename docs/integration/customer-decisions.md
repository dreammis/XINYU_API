# 接入时缺少什么，应该研究；缺少什么，应该问用户

这里的“用户”指平台负责人或需求提供方。先从 A 实现、B 当前配置、C 项目记录、用户历史决定取事实。已经给出的决定不重复询问；技术选型可以从证据确定时由 AI负责。遇到必须由业务方决定的项，先完成不依赖它的工作，再集中询问。

## AI 自己查清的技术问题

- A 实际路径/鉴权/参数/默认值、部署版本、限制、终态和媒体结果。
- B 当前适配器/插件能力、完整协议兼容性、路由/模型选择、插件签名、URL限制、字段消费位置。
- 当前渠道、价格模式、现有分组、已授权凭证与额度、真实运行状态。
- 需要开发哪个插件/适配服务，部署在哪里、依赖什么、测试怎么验证。
- 公开接口缺字段、规范和实现矛盾时回代码/测试修正，不向用户问“哪个值猜起来合理”。

结果写项目 research/newapi-integration.md、upstream/api.md、channel.md。资料不足时按 research-newapi.md 沿当前版本源码查；明确查过什么、缺少哪个证据，不把“我不熟悉 New API”当作提问理由。

## 无法从现有决定推出时，才问的业务问题

| 需要确认什么 | 为什么不能自行定 | 应提供什么具体选项/上下文 |
| --- | --- | --- |
| 对客户开放哪些功能/模型 | A 实现了不代表都允许售卖 | 列实际稳定能力与未验证能力，建议首期范围 |
| 客户调用方式与兼容目标 | 专有接口/现有 SDK兼容属于产品选择 | 给已能实现的路径与参数例子，说明异步/stream 的用法与耗时 |
| 收费单位、售价、币种、分组优惠 | 成本和代码不能代替商业售价 | 给可验证单位、成功/失败结算方式；历史售价先注明日期 |
| 失败、取消、部分成功收费 | 有技术可实现选项，需明确承诺 | 说明现有 B 行为及改动代价，不承诺未实现取消 |
| 客户分组与上线范围 | 谁能用、何时开属于业务范围 | 复用现有 default 或限定测试组等实际可选项 |
| 渠道选择和能力取舍 | 不同源头可能有质量/成本/限制差异 | 展示真实差异，确认是否统一模型名、是否允许切换 |
| 文件/产物保留、分享和隐私 | 下载链接生命周期与数据保留影响客户 | 给实际存储/链接行为，确认需要保留多久和访问范围 |
| 破坏性接口变更、旧版本退役 | 会影响现有客户 | 给兼容影响、迁移与下线安排 |
| 真实验证缺少预算或密钥 | 没有凭证/额度不能完成真实验收 | 点明缺客户 Key、上游权限或具体测试额度；已有授权继续使用 |

可以合并成一次问题：“本次开放哪些功能，收费单位/售价与失败退款怎样约定，先给哪些分组？现有确定项是……，仍缺的是……”。仅缺一项就只问一项。不要为了填满表格问无关政策、也不额外制造审批流程。

## 缺条件时照样交付可验证结果

在项目研究记录用“已确定 / 待业务决定 / 待技术验证”写明每一项的来源和影响。需要决定才能完成的动作等答复；不依赖的代码测试、接口草案、配置差异和本地页面继续做。不将未验证价格、能力或运行状态写成已上线公开事实。

用户会话中的授权优先，并跨后续步骤持续有效；不因为 SOP 有“部署”字样重复请求许可。另一个工程的 AI 需要的信息存文件，不能依赖用户重新解释聊天历史。
